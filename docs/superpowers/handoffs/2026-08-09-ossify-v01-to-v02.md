### ⚠ The tag is orphaned, and it labels a worse tree than shipped

**`ossify-v0.1.0` dereferences to `bbd785c`, which is not an ancestor of `main`.** PR #117 was **squash**-merged into `a5d61f1`, so the branch commit the tag was cut from never entered main's history.

Worse than cosmetic: `bbd785c` predates the Codex P2 round that ran on the PR. `git diff ossify-v0.1.0^{} main -- ossify/` is **15 files / 133 insertions** — the tag is missing four of the major fixes that actually shipped. Anyone checking out `ossify-v0.1.0` gets a tree that is strictly worse than `main`.

**Remedy (not applied — moving a published tag is the user's call):**
```bash
git tag -f -a ossify-v0.1.0 a5d61f1 -m "ossify v0.1.0 — Plan C1 complete"
git push --force origin ossify-v0.1.0
```
Or leave it and cut `ossify-v0.1.1` at `a5d61f1`, which avoids rewriting a published ref. **Decide before v0.2 work starts** — a wrong v0.1.0 anchor makes every later "changed since v0.1.0" diff wrong too.

**Also worth knowing about #118** (`a5d93fc`, 212 files / 32,609 insertions): it brought in the whole ossify tree *plus* `package.json`, `tests/test-opencode-live.sh` and a 3,201-line `tests/test-opencode-runtime-adapter.mjs` at the repo root. **3.3 — The audit deliberately does NOT re-report the C1 correctness findings, and carries a subsumption map.** It is a *quality-and-depth* audit, not a prose-vs-code truth audit. Seven C1 findings are absorbed by audit enhancements (its "C1-findings subsumption map"); the rest are explicitly left as separate v0.2 correctness work. **Do not treat the two documents as one backlog** — dedupe through that map or you will do several items twice.

**3.4 — Two audit sequencing constraints are load-bearing and easy to miss.**
- **Batch E (bloat/token budget) must land before `doctor` ships in v0.3** — the 6th entry-skill description pushes past the budget band. C1 already had to trim five descriptions from 4,180 → 3,121 chars (0.52% → 0.39% of a 200k window) to get inside §9.1's target. There is very little headroom left.
- **WI-3 through WI-6 must land *with* the v0.2 entry-point fix.** Making the round-orchestration lane reachable without fixing its content gaps ships a lane that works and misleads.

**3.5 — The pre-dispatch plan sweep found a defect in all 14 C1 tasks. It is not optional overhead.** Two were P0s where a git operation succeeds at **rc 0** while landing work on the wrong branch. One was a test clause that was green under both the correct and the broken selector it existed to catch. Budget a sweep before every dispatch in v0.2.

**3.6 — Five of my fourteen plan corrections introduced a defect of their own.** A correction is new code and deserves its own sweep. The sharpest form is *prose-right/command-wrong*: the sentence says the right thing while the command computes something else (`git diff A..B` is not a range; a payload key gets renamed by the apply-op). **Run every git/shell/jq idiom you write into a plan — do not reason about it.**

**3.7 — A wrong-target git operation succeeds at rc 0.** Three separate P0s this series were merges landing on the wrong branch with every rc check green. Any assertion over a git operation must check a **concrete observable** — a sha's reachability, a branch name, a file in a tree — never rc alone.

**3.8 — v1 is gated on evidence, not features.** The roadmap now distinguishes *experimental OpenCode installability via the root bundle's four-plugin allowlist* from *stable Claude/Codex marketplace registration*. The former is a v0.x path; only Plan D's consolidated eval **plus the two pilots** earn v1. Do not let the OpenCode path get read as "shipped".

- **Do NOT copy a base commit out of any document.** Re-read `git log` when you generate a review package (§2). Three predecessors got this wrong.

- **Do NOT re-plan v0.2 from the roadmap's original 7 majors** — four are struck through as resolved in PR #117 (§3.2).
- **Do NOT trust an rc code alone over a git operation** (§3.7).
- **Do NOT let a plan correction ship unswept** (§3.6).
- **Do NOT add `doctor`'s description without doing Batch E first** — the entry-skill listing has almost no headroom under §9.1's ≈0.3–0.4% band.
- **Do NOT register ossify in `.claude-plugin/marketplace.json`** or add a `.codex-plugin` manifest. Plan D's ship gate; early registration breaks `tests/test-codex-dual-publish.sh`, which needs both together.
- **Do NOT reason about shell semantics under zsh** — it runs the last pipeline element in the parent shell and hides an entire bug class. `run-all.sh` forces `bash`.
- **Do NOT touch `README.md`** — the user's own uncommitted edit.
- **Do NOT `git add -A`** — always explicit paths.
- **`plan-spine` and `start` are at exactly 499/500 lines.** Any edit adding a line needs a trim in the same commit.
- **architect-critic — the only supported form:** `export ARCHITECT_CRITIC_ARGS="--spec \"<abs path>\" --close"` then a bare `Skill(architect-critic:critiquing-spec)`. No `target=`/`depth=`; both failure modes are silent.
- **Git ops:** the agent does all of them. The auto-mode classifier still blocks `gh pr merge` and direct `git push origin main` until explicit in-turn authorization.
