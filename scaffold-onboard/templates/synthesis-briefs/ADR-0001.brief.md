## Synthesis guidance

This is the foundational ADR that establishes the practice of recording
architecture decisions for the project. It follows the Michael Nygard ADR format.

Status: set to "Accepted". This ADR is always accepted at project bootstrap.

Context: synthesize a project-specific context paragraph that explains WHY this
project needs ADRs. Draw from MASTER-SPEC Phase 4 and Phase 5 to surface the
concrete architectural decisions already made (auth model, tenancy, architecture
shape, primary language(s), primary data store(s)). The context must name the
project class (phase_5.1.1) and highlight any Phase 4 choices that constrain
future architecture (e.g., a specific auth model or multi-tenancy boundary). This
makes the ADR record meaningful rather than a generic template.

Decision: state that the project will use Architecture Decision Records as described
by Michael Nygard, filed under `docs/adr/`. Include the file naming convention
(`NNNN-<slug>.md`, zero-padded, never reused) and the required sections per ADR
(Status / Context / Decision / Consequences). List the allowed Status values:
Proposed, Accepted, Deprecated, Superseded by NNNN. Note that the `scaffold-dev`
plugin's `/adr` command supports fast authoring.

Consequences: enumerate both positive consequences (decisions are traceable,
future contributors understand architectural constraints) and the one negative
constraint (ADRs do not capture every implementation detail, only decisions that
constrain future work). Add any project-specific consequence visible from the
MASTER-SPEC — e.g., if the project has a complex data model, note that data-store
and schema decisions will each warrant their own ADR.
